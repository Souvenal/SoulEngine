# Windows Xmake package diagnostic reference

Load this reference for Windows failures while xmake fetches, builds, or resolves third-party packages (xmake-repo or the project-local souvenal-repo). Use the exact failure signature to choose the smallest repair.

| Signature | Likely cause | Repair | Do not do |
| --- | --- | --- | --- |
| Package build fails at `Building RC object .../assimp.rc.res`; errors are C4335 ("Mac file format") and C2018 ("unknown character U+xxxx") attributed to `rc.exe(<line>)` itself | cl.exe diagnostics, not rc.exe: assimp's CMake defaults `ASSIMP_BUILD_USE_CCACHE=ON` and sets ccache as global `RULE_LAUNCH_COMPILE`. Under the Ninja generator the launcher lands between cmcldeps and rc.exe, so cmcldeps' cl-based dependency-scan pass receives rc.exe as an input file and cl.exe tries to compile rc.exe's PE binary. The `.rc` source on disk is clean ASCII. The VS generator is unaffected because it ignores `RULE_LAUNCH_COMPILE`. | Require assimp from souvenal-repo with `use_ccache = false` (`add_requires("assimp", {configs = {use_ccache = false}})` in `Engine/Source/ThirdParty/personal/xmake.lua`); the recipe maps it to `-DASSIMP_BUILD_USE_CCACHE=OFF`. Verified with `xmake f -c -y`, full `xmake -y`, and `xmake test -j1`. | Edit `assimp.rc`, change Windows codepage/UTF-8 settings, uninstall ccache, or patch the global xmake-repo clone (xmake's periodic "updating repositories" wipes local recipe edits). Do not conclude "ccache is fine" from a manual `ccache rc.exe` invocation or from a successful VS-generator build: pass-through works standalone and only breaks inside the cmcldeps-wrapped Ninja rule. |
| Project source fails with `C2065: SLANG_UNKNOWN_SIZE` or `C2660: slang::TypeLayoutReflection::getElementCount` although a `slang` package is installed | The build resolved slang v2025.11.0 (old reflection API) instead of the pinned `slang[embed_stdlib_source=false] vulkan-sdk-1.4.350.0` from souvenal-repo; the pinned headers define `SLANG_UNKNOWN_SIZE` and the defaulted `getElementCount(SlangReflection*)` parameter. | Force re-resolution with `xmake f -c -y`, then rebuild. Confirm via the compile lines that the slang include path contains `vulkan-sdk-1.4.350.0`. | Trust `xmake require --info slang`: it re-resolves the package standalone and displays the latest version with default configs, not the project's pinned require. Do not run `xmake require <name>` without a version to "fix" a pinned require; it installs the unpinned latest and leaves both versions on disk. |
| `clone https://github.com/<repo>.git <tag> .. failed` during package install, with a stale `source.tmp` left in the package cache dir | Transient network failure to GitHub (the host routes through `proxy_pac = pac.lua`); not a recipe defect. | Retry; verify reachability first with `git ls-remote --tags <url> <tag>`. xmake re-clones over the stale `source.tmp` on the next attempt. | Switch the package URL, fork the recipe, or manually seed `pkg_searchdirs` before confirming the network is the actual failure. |

## Project package-resolution facts

- A `package("<name>")` defined in the project **fully replaces** the same-named xmake-repo recipe; there is no field-level merging, so an override must carry the complete recipe (versions, deps, `on_install`, `on_test`).
- Repo lookup order for recipes is project-local repositories (`.xmake/<plat>/<arch>/repositories/`) plus global ones; AGENTS.md warns that `add_repositories()` can be silently ignored in favour of official repos, which is why durable recipe fixes belong in inline `package()` definitions.
- xmake's own `ccache = true` project config only wraps xmake-driven compiler invocations and is unrelated to assimp's CMake-level `RULE_LAUNCH_COMPILE` failure above.
- Packages that pull `vulkan-headers` transitively (e.g. `imgui[vulkan]`, `vulkan-memory-allocator`) use the recipe's stock configs, so xmake installs a second `vulkan-headers#1` variant next to the project's custom-config one. `Engine/Source/ThirdParty/xmake.lua` pins every known transitive path onto the shared `vulkan_header_configs` table via `add_requireconfs("<parent>.vulkan-headers", ...)`; extend that list when another package starts depending on vulkan-headers. Verified with `xmake f -c -y`: exactly one `install vulkan-headers 1.4.350+0` line, and imgui resolves to that same variant.
