# Xmake repository resolution reference

Cross-platform failures while xmake resolves which repository a package recipe comes from (before any download/build). For fetch/build/resolution failures of already-found recipes on Windows, see windows-xmake-packages.md.

| Signature | Likely cause | Repair | Do not do |
| --- | --- | --- | --- |
| `xmake f` stops right after the platform/SDK checks with `note: the following packages were not found in any repository ... -> <pkg>, maybe <other> in xmake-repo` followed by `error: <no error object>`, and the recipe provably exists in a registered repo | Two compounding causes. (1) `network = "private"` in the global xmake config (`~/.xmake/xmake.conf`) makes `pulled()` in `private/action/require/impl/repository.lua` return true unconditionally, so `xmake f` never auto-runs the repo-update task and a missing project-local repo clone (`.xmake/<plat>/<arch>/repositories/<name>`) is never created. (2) xmake caches repo instances by name only (`repository._REPOS[name]`), so when the same repo is registered both project-local (via `add_repositories`) and global (via `xmake repo --add -g`), the global clone (e.g. `~/.xmake/repositories/<name>`, which may hold the recipe) is shadowed by the missing local one and never searched. The opaque `error: <no error object>` is a bare `raise()` at `install_packages.lua` after the recipe lookup fell back to a nonexistent system package. | Run `xmake repo -u` manually (works in private network mode) to clone the project-local repo, then `xmake f -y`. Verified 2026-09-29: imgui-club resolved and installed, `xmake f` exit 0. Durable alternative: remove `network = "private"` from `~/.xmake/xmake.conf` (or `xmake g --network=public`) so `xmake f` auto-clones missing repos again — but only if the private setting was not deliberate. | Do not conclude the recipe is missing from the remote repo and do not re-fork/edit recipes. Do not expect the global clone of the same-named repo to be searched — it is shadowed. Do not trust a later successful `xmake f` as proof the repo issue is gone: once resolved, package info is cached in `.xmake/<plat>/<arch>/cache/package` and the recipe lookup is skipped until forced reconfig (`xmake f -c`) or cache invalidation. |

## Debugging techniques that located this

- `xmake repo -l` lists both project-local and global repo registrations; a project-local registration with no matching `.xmake/<plat>/<arch>/repositories/<name>` directory is the failure shape.
- `xmake lua <script>` with `import("private.action.require.impl.repository")` can dump `repository.repositories()` (name/directory per instance — reveals same-name shadowing) and evaluate `repository.pulled()` directly.
- xmake's sandbox `print` stops at the first nil argument; use `print(format("%s", tostring(x)))` when probing possibly-nil config values (this initially hid `network = "private"`).
- The three `not found in any repository` sites differ: `package.lua` raises `package(<name>) not found!`; the `install_packages.lua` / `download_packages.lua` sites use a bare `raise()`, which renders as `error: <no error object>` and means "recipe lookup failed and system fallback does not exist".
