# Context: RHI

**Namespace:** SoulEngine

Render Hardware Interface — abstract GPU layer. Backends register through the self-registering factory. The RHI boundary owns native-resource construction, submission lifetime, and native destruction; higher layers carry RHIRef<T> handles and record declarative commands.

## Terms

| Term | Definition |
|------|------------|
| **RHIRef<T>** | Copyable handle to a shared RHIRefPayload<T>. It represents a particular backend-native resource without exposing ownership of the native T. States are RhiCommitting, Ready, and Failed. Its explicit `operator bool()` is true only when the payload exists and is Ready; `operator->`/`operator*` provide access after that guard. `TryGet()` remains the explicit nullable access path for backend lowering. |
| **RHIRef payload** | Shared state containing the atomic availability state, optional error, and the native UPtr<T>. Its final destruction moves the native object into the deferred-deletion queue rather than destroying it on the releasing thread. |
| **Deferred deletion queue** | Thread-safe queue of move-only destruction callbacks owned by the RHI module itself (module-level storage behind GDeferredDeletionQueue). Last-ref release may enqueue from any thread; RHILoop drains it on the RHI thread once per frame via DrainRHIDeferredDeletions(), and backend Shutdown() performs the final flush. It is valid only between RHIRenderDevice::Create() and Destroy(). |
| **CommandList** | Move-only frame packet containing ordered pass entries (graphics, compute, transfer, ray tracing) and optionally an ImGui presentation overlay. Every resource-bearing command field uses RHIRef<T> rather than an owning or observer pointer. |
| **Pass entry / prologue** | The frame packet's unit: `RHIPassEntry { Pass, Prologue }`. The prologue is the pass's destination-only transition set produced by the RenderGraph from declared accesses (ADR 05): a transition is a view plus a stage mask — the native access mask and image layout derive from the view's (Usage, Access) in the backend mapping, so the vocabulary carries no layout axis. A transition is a declaration, not a barrier; graph-created and imported resources both participate. |
| **Barrier diff tracker** | The backend's emission-side, single-writer (RHI thread) state cache. It materializes one native barrier when a prologue's desired state differs from the tracked state and emits nothing when equal. Its update sources are restricted to prologue transitions and backend-reserved sites (swapchain acquire/present, texture uploads, host belt writes, AS builds); binding/command side effects never feed it. Every resource state change flows through it — imported-resource prologue correctness rests on that total coverage. Pooled transient images start each frame from `Undefined`; imported persistent resources are tracked cross-frame. |
| **Pass / scope** | A graphics, compute, transfer, or ray-tracing RHIPass containing declarative RHICommand work. One graphics RHIPass owns an ordered color-attachment list plus an optional depth attachment and may bind multiple compatible graphics pipelines. Attachments, pipelines, draw buffers, shader-parameter resources, TLAS/BLAS instances, and presentation source are ref-backed. Color and depth attachments can explicitly load instead of clear when a post-process overlays an existing target. |
| **Frame completion** | Backend-independent token returned by EndFrame(). The owning FrameSlot retains its RenderResult until WaitFinish() confirms GPU completion. |
| **Shader parameters** | Copyable CPU-side values partitioned by reflected descriptor-set layout. RHIShaderParameterResources carries ref-backed textures, samplers, and buffers used by that snapshot. |
| **Transient buffers and belts** | `CreateBuffer` with `Lifetime = Transient` registers an immediately-returned ref whose belt slice (uniform or shader-storage belt, chosen by the usage bits) is resolved by the RHI frame task as a bump allocation out of the backend ring. Bytes never ride creation: `UploadBuffer` on a not-yet-materialized transient ref is legal and validates at task time (same-frame frame tasks run FIFO), writing the slice in place through its persistent mapping; a generation guard drops cross-frame uploads (a transient ref retained past its creation frame — a contract violation the frame-task ordinals cannot see, because the misused upload's task ordinal still matches the current frame). A transient ref is valid only for the logical frame in which it was created. |
| **RenderDevice** | Process-wide RHI singleton. Persistent-buffer, texture, pipeline, binding-set, and AS creation run synchronously on the calling thread (resource creation is thread-safe: VMA locks internally, vkCreateBuffer/vkCreateImage are device-level); sampler creation still queues native construction to ThreadQueue::RHI. Descs never carry data — uploads are decoupled into UploadBuffer/UploadTexture (see Pending upload), and AS builds are likewise decoupled into BuildBlas/BuildTlas (frame-affined tasks carrying only the ref; the backend bakes a self-contained build entry from the materialized payload, and the build is recorded in the frame-start AS phase of the issuing frame, after the upload batch). Execute() consumes the whole RenderResult frame packet; the pure-virtual Tick() is the frame-begin hook on the RHI thread — backends retire native completions there and stamp frame-boundary retirement bookkeeping (e.g. the previous frame's pending upload markers). Deferred destruction is drained separately by RHILoop through DrainRHIDeferredDeletions(). |
| **Pending upload** | A full-resource upload requested through `RHIRenderDevice::UploadBuffer`/`UploadTexture` (any thread): the contract below is shared; textures upload full mip-0 texels into the batch's image lane (buffer→image copies wrapped in image-tracker transitions, destination images sharing the no-retention guarantee). the call snapshots the bytes and enqueues a frame-affined task tagged with the producer's frame ordinal; all memory writes happen on the RHI thread. For CpuToGpu buffers the task copies straight into the host-visible allocation, and for transient slices it writes the belt range in place (no staging, no batch entry). Host-visible writes carry no barrier anywhere: belts are contractually host-coherent and host writes are implicitly visible to later submissions (the D3D12 UPLOAD-heap and Granite linear-allocator precedent). For GpuOnly buffers the RHI thread drains the frame's tasks before Execute — staging allocation and host copy happen there — and the frame-start upload batch records one copy per entry plus one aggregated transfer-write → consumer-read barrier ahead of the BLAS batch, which reads geometry buffers. Frame affinity makes one producer frame's uploads land atomically (no cross-buffer skew); staging ranges retire via the backend staging ring's timeline markers, and destination buffers need no retention — final native destruction is deferred past GPU completion by the backend (see item 4 of the contract below). Per-entry failure skips and logs (BLAS precedent); there is no retry. |
| **Ready resource** | A ref for which `operator bool()` is true and whose payload can be read through `operator->`, `operator*`, or `TryGet()`. A persistent buffer is Ready at creation return (synchronous allocation; device address immediately bakable); a texture is likewise Ready at creation return — UploadTexture bytes land in the frame-start upload batch's image lane, safe by submission order, the same contract as GpuOnly buffer uploads. |
| **Resource kinds** | Exactly three: `RHIBuffer`, `RHITexture`, and acceleration structures (ADR 05). Vertex/index/constant/storage/indirect/sampled/render-target are usages, not types — the creation Desc carries the usage-flag union (`RHIBufferUsage`/`RHITextureUsage`) as an allocation-legality property, and the backend dispatches on it. `RHISampler` is a state object, not a resource. |
| **View (RHI)** | Value-semantic `(resource, usage, extent, access)` tuple — `RHITextureView{Texture, Usage, Range, Access}` / `RHIBufferView{Buffer, Usage, Offset, Range, Access}`, field order identity → role → extent → direction (ADR 05). Not an `RHIObject`; commands and bindings hold views, lifetime comes from the embedded resource ref, and the backend resolves/caches native views at record time. A view carries Usage and Access (Read/Write, `RHIAccess` from :Types) but never Stage (a pass property, ADR 05) — one view, one role; the creation union lives only on the Desc. Image layout is likewise absent from the view: it is a pure function of (Usage, Access), derived in the backend mapping at emission (ADR 05). Degenerate views `RHISamplerView` / `RHITlasView` carry identity only (a sampler is a state object, a TLAS binds whole — neither has role/extent/direction axes); they exist so shader bindings retain their payload through the embedded ref like every other view kind. |
| **Buffer lifetime** | `RHILifetime { Unknown, Persistent, Transient }` on `RHIBufferDesc` — the frame-graph vocabulary (UE RDG, Frostbite FrameGraph): Persistent buffers are individually owned and outlive frames; Transient buffers are per-frame belt slices valid only for their creation frame. `CreateBuffer` is the single creation entry, dispatched on Lifetime × MemoryUsage; every flavor returns the same `RHIBuffer` identity. Lifetime is stored on the `RHIBuffer` identity (`GetLifetime()`) and discriminates the backend's per-flavor state: the Vulkan backend holds a `std::variant<PersistentBufferProp, TransientBufferProp>` so mixed-flavor member state is unrepresentable; `GetProp<T>()` is the only access path to flavor state. A Desc is explicit (every field defaults to an Unknown/0 guard) and is a pure data carrier: validation and flavor dispatch live in the backend's buffer manager at creation — tolerance is a backend decision. Graph-registered buffers are transient by construction — the graph stamps Lifetime at realize. |
| **Texture** | `RHITexture` — the single image identity (ADR 05): attachments, sampled uploads, storage images, and copy endpoints are usages on `RHITextureDesc`, never types. The Desc also carries the `RHIMemoryUsage` placement axis (mirroring `RHIBufferDesc`): GpuOnly derives transfer-dst capability at creation (the UploadTexture path) and is the only supported image placement. Graph-created transients are pooled by RenderGraph (the graph stamps GpuOnly at registration); usage is declared at creation and checked against the graph's view declarations at Compile (ADR 05). Mip level count is a creation-time property (default 1, partial chains legal). |
| **Mip chain** | A texture's mip levels, created eagerly at creation time (1..N levels, N ≤ floor(log2(max(w,h)))+1). The RHI layer exposes `GetMipLevelCount()`; subresource selection is a view property — `RHITextureView.Range` names the whole chain (default) or one mip, and the backend resolves the matching native image view. |
| **Present** | The explicit `RHIBlitToSwapchainCmd{Source, DstRect}` (fixed Nearest filter), issued by a transfer pass. It always blits the complete source target into the destination viewport; the backend visitor resolves the acquired backend-private swapchain image. There is no present flag on passes, views, or usage bits. |
| **Texture usage** | `RHITextureUsage` flags: RenderTarget, DepthStencil, Sampled, Storage, TransferSrc, TransferDst — flag composition comes from Core (`Core:Util.Flags`): one exported `operator|` in `namespace SoulEngine`, constrained to enums that set `magic_enum::customize::enum_range<E>::is_flags`, so importers compose flags via ADL with no per-file using while Vulkan's `vk::` flag operators keep their own resolution; test via `magic_enum::enum_flags_test`. FrameOutput was removed (ADR 05). The creation Desc carries the usage union; transfer-dst capability derives from GpuOnly placement automatically (the UploadTexture path), never from a usage bit. Buffer counterpart: `RHIBufferUsage` (Vertex, Index, Constant, Storage, Indirect, TransferSrc/Dst) — TransferSrc/Dst double as the graph-side view/sync declaration axis. Native-usage mapping functions are pure flag mappings; placement-derived capability lives at the creation site. |
| **Swapchain image** | Backend-private presentation image; never an engine-owned sampled texture or an RHIRef exposed to Renderer. |
| **Graphics / ray-tracing pipeline** | Backend-polymorphic pipeline payload retained by bind, draw, push-constant, parameter-binding, or trace commands. |
| **Compute pipeline** | Backend-polymorphic compute pipeline payload. Host-provided specialization constant values are fixed at creation (`VkSpecializationInfo`) and are part of the pipeline identity: two value sets must yield two pipelines. |
| **Frame-affined task** | A TaskGraph callback tagged with the producer thread's frame ordinal. The RHI queue executes only callbacks matching the current RHI thread ordinal. |
| **Transient data upload** | A transient RHI resource creation task owns a byte snapshot, bump-allocates the current Vulkan belt's ring, writes the data through the range's persistent mapping, and publishes a Ready `RHIRef` before command recording. |
| **RHIReadback** | GPU→CPU readback identity — a consumer object, not a resource kind (no views, no binding, no upload; same category as RHISampler). Created via `CreateReadback(Name, SizeBytes)` — synchronous, Ready at return, the backend derives the ring depth as frames-in-flight + 1. A transfer-stage-class pass records `ReadbackTexture(source, rect, stream)`; the destination ring is a backend-internal sync site, never a graph resource, so the pass declares only the source's TransferSrc read and carries `NeverPrune` (the graph-invisible ring write would otherwise let Compile prune the pass). Reading is game-thread polled newest-completed semantics: `TryRead()` returns the payload bytes, empty when no write has completed. Contract: at most one write per frame per stream — the reader's newest-completed slot and the allocator's oldest-slot victim stay disjoint. |

| **Buffer memory usage** | `RHIMemoryUsage { Unknown, GpuOnly, CpuToGpu }` — the allocation-placement property on `RHIBufferDesc`, named after the VMA (`VmaMemoryUsage`) / The-Forge (`RESOURCE_MEMORY_USAGE`) / D3D12 heap-type (DEFAULT/UPLOAD/READBACK) vocabulary. Placement decides capability and upload mechanism: GpuOnly derives transfer-dst and device-address capability at creation and uploads through the frame-start staging batch; CpuToGpu is host-visible, carries neither capability, and its UploadBuffer is an RHI-thread memory copy (low-frequency writes only — the caller owns the WAR contract against in-flight GPU reads; per-frame data belongs in transient belts). GPU→CPU readback is not a placement — see the RHIReadback term. |
| **Buffer device address** | `RHIBuffer::GetDeviceAddress()` exposes the address value used by current shader ABI records. Every GpuOnly buffer carries one (BDA costs nothing at creation, so it is not a usage opt-in); host-visible and transient flavors return 0. |

## Submission and destruction contract

1. A caller asks RHIRenderDevice to create a resource and receives an RHIRef. The Vulkan backend queues the native creation closure on ThreadQueue::RHI.
2. Render code records ready refs. Transient refs are immediately ready logical frame resources; their RHI frame task resolves the belt slice before Vulkan command recording. The command list takes copies/moves of the refs, so command recording does not depend on raw RHI observers.
3. Vulkan records and submits the borrowed list, then returns an RHIFrameCompletion token containing the graphics timeline value signalled by that submission. The owning FrameSlot retains the list until WaitFinish() reports completion.
4. Releasing the last RHIRef moves the native object into the module-level deferred deletion queue — the cross-thread transport hop. RHILoop drains the queue on the RHI thread after Tick() each frame; the drained destructor hands the native handles to the backend's GPU-retirement queue (the Vulkan backend stamps destruction as a virtual timeline event), so final native destruction lands only after the GPU has passed the destruction frame's submission. For a submission-held ref, this cannot happen until the submission is complete.

The command-list lifetime is therefore **FrameSlot-owned**. Execute() borrows the slot's list for recording; EndFrame() returns a completion token without moving the list. RenderThread waits for both RHI's CPU-side packet consumption and the token's GPU completion before replacing the slot's RenderResult.

RHIImGuiPresentationOverlayCmd is the current exception to ref-backed command payloads: it contains non-owning ImGui snapshot/texture-queue/mutex pointers that need to remain valid only through Execute(). Its backend texture objects are managed by Dear ImGui rather than by RHIRef; do not extend this exception to ordinary RHI resources.

## Thread model

| Operation | Required thread / current behavior |
|-----------|------------------------------------|
| CPU request preparation and RHIRef state reads | Any thread. `operator bool()` is the Ready guard; `TryGet()` and `operator->` are state-gated reads, not permission to mutate native state. |
| Persistent-buffer/texture/pipeline/binding-set/AS creation (synchronous) and UploadBuffer/UploadTexture/BuildBlas/BuildTlas (frame-task enqueue only) | Any thread during normal runtime. |
| Sampler native creation, upload-task staging (ring slice + host copy into the frame-start batch's buffer/image lanes), Execute(), Tick(), and the RHILoop-driven deferred deletion drain | RHI thread during normal runtime. |
| `WaitFinish()` | RenderThread; read-only host wait on an immutable completion token. |
| RHIRef last-release | Any thread; it only enqueues the native destructor. |
| Device initialization and final shutdown | Main thread today: RHIRenderDevice::Create() runs during EngineLoop::Init(), and Destroy()/backend Shutdown() run after the RHI thread joins. These are explicit lifecycle exceptions, so the code does **not** yet enforce a strict all-RHI-context-calls-on-RHI-thread rule. |

## Relationships

- Scene, Renderer, Editor, and other higher-level owners keep RHIRef values; a recorded command owns the RHI-lifetime portion through copied RHIRef<T>.
- A caller that owns a borrowed command list must retain every ref-backed command resource until that submission is no longer GPU-visible. The backend returns an RHIFrameCompletion token so the caller can wait at the packet replacement boundary.
- Payload readiness is separate from submission lifetime: only a Ready payload is recordable; an in-flight submitted Ready payload remains alive through command-list retention.
- Frame-affined transient creation tasks retain byte snapshots until the RHI thread allocates/writes the payload in the current belt. The transient ref is created Ready, but it cannot be retained or rebound after its creation frame. The command list retains the ref while the backend records and submits that frame.

## Transient data upload

Uploadable records define a nested `GpuData` ABI and a `BuildGpuData()` member that constructs it directly from their RHI buffer members and scalar fields. Renderer code creates a transient buffer from the resulting byte snapshot and stores the immediately-ready `RHIRef` in shader parameters or commands. The RHI frame task bump-allocates and writes the current backend belt's ring, then fills the backend transient object's ring offset. Vulkan binds that offset directly and emits one aggregated host-write visibility barrier for UniformRead, ShaderRead, and IndirectCommandRead consumers.

## Current gaps / guardrails

- GDeferredDeletionQueue is a process-wide raw pointer. A payload whose last ref is released after RHIRenderDevice::Destroy() would dereference a null queue; shutdown order must release all refs first.
- Tick() retains a documented RHI-thread precondition without a runtime thread-affinity assertion; deletion draining is now driven structurally by RHILoop (plus backend Shutdown() for the final flush).
- The FrameSlot reset point and the backend submission-retention point are deliberately different today. Do not claim slot reuse itself proves GPU completion.
- The generic RHI interface does not yet expose a backend-independent submission retirement contract; a new backend must provide one before using RHIRef.
- Current-frame CPU-to-GPU uploads belong in frame-affined transient creation tasks, not individual RHICommand upload variants or scopes. New uploadable data must provide a GPU ABI record and materialize its bytes before calling CreateTransientBuffer().

## Dependencies
